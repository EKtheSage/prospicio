# Agent instructions

Shared guidance for every coding agent working in this repo: local Claude Code, Claude Code cloud sessions, and Codex. `CLAUDE.md` imports this file.

## Several agent sessions at once

A local session and one or more cloud sessions may be working on this repo at the same time. They do not share a working tree. The GitHub remote is the only thing they have in common.

- **One branch per session.** Never push to a branch that another session owns. Cloud sessions use `claude/<name>` branches.
- **Stack a batch from one session.** When one session opens several PRs in the same lane, base each branch on the one before it (`git worktree add -b <next> ../risk-rs-<next> <previous-branch>`) and say in each PR description which PR it builds on, so they merge in order without conflicts; nine PRs opened from one base cost eight re-merges of the same files (#853). After the one below merges, merge `main` into the next and re-target it to `main`.
- **One git worktree per session or task.** Start every piece of work in its own worktree, never in the main checkout, so that uncommitted edits, builds and branches of different sessions cannot mix: `git fetch origin && git worktree add -b <branch> ../risk-rs-<name> origin/main`, then work, run the checks and push from there, and open the PR from there. The main checkout (`risk-rs/`) holds whatever the user is editing by hand: do not write into it, stash it or reset it. The editing tools resolve relative paths against the main checkout and refuse paths outside the workspace, so edit worktree files through the shell with absolute paths, and check `git status` in the main checkout afterwards. When the PR merges, `git worktree remove ../risk-rs-<name>` and delete the branch. `git worktree list` shows what exists.
- **Nothing is visible until it is pushed.** Commit and push often enough that other sessions can fetch your work. Before you start work that depends on another session, run `git fetch` and look at its branch.
- **Stay inside your assigned scope.** The user gives each session its own work (crates, files, or a phase). Do not edit files outside that scope without asking. If you must, say so clearly in your PR.
- **Merge through PRs into `main`.** Only the user merges. After a merge, other sessions rebase onto or merge `main` before they continue.
- **Record shared decisions in the repo.** Put them in this file or in `docs/`, not only in chat, so every session picks them up on its next pull.
- **Record collected knowledge in `knowledge/`.** Facts found while working (datasets, reference implementations and their quirks, numerical findings, environment facts) go into the bundle in `knowledge/`, in the [Open Knowledge Format v0.2](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/main/SPEC.md): one markdown file per concept with YAML frontmatter (`type`, `title`, `description`, `tags`, `sources`, `generated`, and `verified` when a test that CI runs confirms it), listed in its directory's `index.md`, with a dated entry written as a fragment in `changes/knowledge/` (see "Change fragments" below), not in `knowledge/log.md`. Design decisions stay in `docs/design/`. `validation/scripts/check_okf.py` checks the bundle in CI.
- **Leave the docs current in the item's own PR.** The PR that finishes an item also updates everything that describes it: its lane's status files in `docs/lanes/` (append its Done bullet to `docs/lanes/done/<lane>.md` and add any new Next items, deleting nothing; see "Lane status files" below), its design note's status and decisions, `docs/roadmap.md` (its lane section and milestone rows) and `docs/architecture.md` if a roadmap row changes, a fragment in `changes/changelog/` for a user-facing change (breaking ones marked), which becomes a line under "Unreleased" in `CHANGELOG.md`, `CLAUDE.md` or this file if a working rule changed, and `knowledge/` (next bullet). Never leave these for a follow-up PR; a reviewer treats a stale status bullet or status as a defect of the PR.
- **Update the knowledge bundle when an item is done.** Before you report a finished work item, add what it taught you to `knowledge/`: new or corrected concepts (a dataset, a reference implementation's quirk, a numerical finding, an environment fact), `verified` on facts that a CI test now confirms, `status: deprecated` on facts it made wrong, and a dated fragment in `changes/knowledge/`. Do it in the item's own PR. If the item taught nothing new, say so in the report.
- **Change fragments, not edits to the shared logs.** `knowledge/log.md` and `CHANGELOG.md` are folded from small files so that PRs running at once do not conflict. A PR never edits those two files for a new entry; it adds `changes/knowledge/<YYYY-MM-DD>-<slug>.md` and, for a user-facing change, `changes/changelog/<slug>.md`, where the slug is the branch name with `/` turned into `-`. `changes/README.md` has the formats. CI runs `validation/scripts/fold_changes.py --check` on every PR. Only one PR folds at a time, so folds do not conflict either: the release PR always folds (`docs/release.md`), and between releases a session folds (`python3 validation/scripts/fold_changes.py`) only when the user asks, in a small PR of its own that contains nothing else. Until a fold, read `changes/knowledge/` together with `knowledge/log.md` for the latest entries. The fold also deletes the lane files' finished Next bullets ("Lane status files" below).
- **Report when an item is done.** When you finish a work item (a PR merged, an issue closed, or a task the user asked for), end your reply to the user with a summary in three parts:
  1. **Work by session**: what each session worked on since the last report: this session's items with their PRs, and the other sessions' merged PRs, from `git log origin/main` and the open PRs.
  2. **Repo status**: `main` (the latest merges and whether CI is green), open PRs and issues, and anything blocked and on whom.
  3. **Next steps**: what comes next in your lanes, in order, and anything waiting on the user.
- **Messages go one way.** A local session can send a cloud session a message, but the cloud session cannot reply. Leave status and questions in your PR description or in commit messages, where the user and other sessions can read them.

### Lane status files

The table above holds only static facts. What a lane will do next lives in its status file, `docs/lanes/<lane>.md` (the lane name in lowercase), with one section, `## Next`; what it has done lives in `docs/lanes/done/<lane>.md`, with one section, `## Done`, which is not imported into every session (#846): read your own lane's done file when you need its history, and the design notes for the decisions. There is no `## Now` section: open PRs are in `gh pr list`, and the PR that finishes an item adds its Done bullet.

- **One bullet per line.** Each item is a single physical line, never wrapped, so that two PRs editing different items never touch the same line.
- **Done is append-only.** A PR appends its Done bullets at the end of `## Done` in `docs/lanes/done/<lane>.md` and never edits, reorders or reflows existing Done bullets. A branch from before the split that adds a `## Done` section to `docs/lanes/<lane>.md` fails `check_lanes.py`; move its bullets to the done file.
- **Every Next bullet carries an id.** The id is the issue number already in the text (the first `#N`, as in `(#392)`) or, when the bullet names no issue, a bracketed slug at the start, such as `[compartmental-pr-e]`. An issue finished over several PRs keeps its remaining work in Next under a slug (as `[odp-glm-designs] #333...`), since the first PR's Done bullet already names the issue. A PR that finishes a Next item appends a Done bullet that repeats the same id (`#N` or `[slug]`) and leaves the Next bullet where it is: the fold deletes it (#853). A PR that adds a Next item gives it an id.
- **Union merge.** `docs/lanes/*.md` and `docs/lanes/done/*.md` use git's union merge (`.gitattributes`: `merge=union`), which keeps both sides' added lines, so concurrent PRs do not conflict. It would also keep lines that one side deleted when another PR changed or deleted an adjacent line, so a feature PR deletes nothing from these files: finished Next bullets wait for the fold (`fold_changes.py`, one PR at a time, or `check_lanes.py --prune` in the same kind of PR of its own), and nothing deleted in parallel can come back (#853). Run `python3 validation/scripts/check_lanes.py` after merging `main` and **before you pick a Next item**: it lists each Next bullet whose id appears in a Done bullet as "finished, to prune at the next fold", which you do not start, and fails on a Next bullet without an id, on a wrapped bullet, on a bullet kept twice and on a Done section in the imported file. CI runs it, after its self-test (`test_check_lanes.py`).
- **Every agent reads every status file before planning.** Claude Code loads them with this file through the imports below (`CLAUDE.md` imports `AGENTS.md`, which imports each status file; the done files are not imported). Codex and any agent that does not expand `@` imports reads `docs/lanes/*.md` at the start of a task. A new lane adds its import line here and a done file.

### Shared files

- **`crates/prospicio-core/`** is used by every lane. Change it only in a small PR of its own that holds nothing else, so it can merge first. Other lanes merge `main` before they build on the change.
- **Bindings**: each lane puts its wrappers in its own module file (for example `crates/prospicio-python/src/reserving.rs`, `crates/prospicio-r/src/distributions.rs`, `R/prospicio/R/reserving.R`, `python/prospicio/reserving.py`). The crate's `lib.rs` only registers modules, one line per lane. A new public type or function in a library crate gets its Python and R bindings in the same PR, or an entry with a one-line reason in `validation/bindings-allowlist.toml`; `validation/scripts/check_bindings.py` checks this in CI and prints the coverage table for the PR description. It counts module-level types and free functions, a type's binding standing in for its methods; the Excel add-in's coverage is reported and never fails it; and the placeholder reasons seeded on 2026-10-28 are a backlog for each lane to bind or explain (the user's decisions of 2026-10-29).
- **Root `Cargo.toml` and `Cargo.lock`**: add dependencies only when a lane needs them. When `Cargo.lock` conflicts, take either side and let `cargo` regenerate it. Do not merge it by hand.
- **Generated files**: `python/prospicio/prospicio_native.pyi`, `R/prospicio/R/extendr-wrappers.R`, `R/prospicio/man/` and `R/prospicio/NAMESPACE` are never merged by hand either. When one conflicts after merging `main`, take either side, regenerate with `cargo xtask generated` and commit what it writes (#853).
- **Registration lists**: `R/prospicio/_pkgdown.yml` and `python/great-docs.yml` list every binding. Add a new name in sorted order within its group, not at the group's end, so that PRs adding names to the same group touch different lines (#853).
- **New tests go in new files.** A new feature's tests go in a file of their own: `validation/tests/<lane>_<feature>.rs`, `python/tests/test_<lane>_<feature>.py` and `R/prospicio/tests/test-<lane>-<feature>.R`, never appended to a large shared file such as `validation/tests/aggregate.rs`, `distributions.rs`, `test_aggregate.py` or `test-aggregate.R`, whose ends every PR in the lane used to extend at the same line (#853). The existing files stay as they are. A new file needs no registration: the validation crate's `build.rs`, pytest and the R loop find it.
- **`AGENTS.md` and `docs/architecture.md`**: a lane updates its own status files (`docs/lanes/<lane>.md` and `docs/lanes/done/<lane>.md`), and the roadmap row its item finishes, in the item's own PR; any other change, including the lane table's Session and Owns columns, goes in a small PR of its own. Each lane edits only its own design notes under `docs/design/`.
- **Releases**: `crates/prospicio` (the umbrella crate), `.github/workflows/release.yml` and `docs/release.md`. A new `prospicio-*` crate gets a `version` next to its path in `[workspace.dependencies]` and a re-export in `crates/prospicio/src/lib.rs`; check it with `cargo publish --workspace --dry-run`.
- **Keep PRs small** (one type or method each) and merge `main` often. The longer a branch lives, the harder its conflicts get.

## Checks

`.github/workflows/ci.yml` runs on every PR and on pushes to `main`. A PR merges only when CI is green on its latest commit.

The repository is public, so CI minutes are not billed; the limits below keep a PR's wait short (#828). PRs run Ubuntu only, the `python`, `r` and `rust` jobs skip a PR that touches only docs, knowledge, change fragments or lane status (`DOCS_ONLY` in `ci.yml`; the `rust` job still runs for the Excel add-in and `xtask`), while the `checks` job (formatting and the Python checks, seconds) runs on every PR (#827), the docs job checks the generated files without rendering a site when a PR touches the bindings, `python/`, `R/` or `ci.yml` (`cargo xtask generated --check`) and renders both sites only when it touches the sites' configuration or `xtask/` (`cargo xtask docs --check --no-tests`; #823; a guides-only PR skips it, its guides run in the `python` and `r` jobs and the sites render on `main`), never running the test suites again, the slow suites run in release builds of their own jobs (`bayes`, in three legs at once, and `fremtpl2`) only when a PR touches their inputs, pytest prints its slowest tests and the R loop each file's time (#826), and the full matrix with Windows runs nightly and on demand (`workflow_dispatch`); `release.yml` runs a dry run every week, building and testing the wheels on Linux x86_64 and aarch64, macOS and Windows, which no PR builds. Cargo builds are cached; a PR can read `main`'s caches but not another branch's, so a push to `main` runs the Rust job's checks and, in the other jobs, builds only what a missing cache needs (the Pages build keeps the docs job's cache warm). A new push to a PR cancels its older run; pushes to `main`, the nightly run and manual runs are never cancelled. Debug builds are optimized (`[profile.dev]` in `Cargo.toml`: `opt-level = 1`, dependencies at 2), since they exist for the tests: a debug `cargo test` takes about a minute, against about seven at `opt-level = 0`. Run the Actions tab's "Run workflow" before a release, or after a change that could break only on Windows. The nightly and manual runs also render the R twins `examples/one_year_view.qmd` and `examples/reinsurance_pricing.qmd` with Quarto and check what they print against the notebooks (the `examples-r` job, #271); pull requests skip it, so after changing an R binding those twins use, run it by hand (`gh workflow run ci.yml --ref <branch>`, which runs the whole nightly matrix, Windows included).

Run the matching `ci.yml` checks locally before you push, so CI does not go red on something a local run would have caught:

- Always: `cargo fmt --all --check`, `cargo clippy --all-targets --features prospicio-validation/slow-bayes -- -D warnings`, `cargo test`, `cargo xtask rust` (rustdoc, warnings denied), `python3 validation/scripts/fold_changes.py --check`, `python3 validation/scripts/test_check_lanes.py && python3 validation/scripts/check_lanes.py`, `python3 validation/scripts/check_bindings.py`, `python3 validation/scripts/check_reference_manifest.py` (every file under `validation/reference/` listed in its `MANIFEST.toml` with its generator and hash; after regenerating a reference file run it with `--update <path>`, and give a new file an entry with its generators, #844)
- Bayesian parity tests: a plain `cargo test` skips them (about 220 s in debug). When a PR touches `prospicio-reserving`, `prospicio-bayes`, `prospicio-prob`, `prospicio-core`, `prospicio-math`, `prospicio-glm`, `prospicio-models` or their validation files, run them in release (minutes now, with the one-year views' refits): `cargo test --release -p prospicio-validation --features slow-bayes --test bayes`, or one file with its module as a filter (`--test bayes reserving_meyers_cay::`). They are the files that `validation/Cargo.toml`'s `[package.metadata.bayes-shards]` names, modules of the one `bayes` test binary (#825); a new Bayesian parity file gets a leg there and nothing else (CI's `bayes` job runs the three legs at once with their modules as filters; `validation/scripts/bayes_shards.py` fails on a name that is no file or is in two legs, #824). The slowest of them, the one-year conformance suite and the Meyers and compartmental one-year validation, run a smoke version (the conformance suite on `BayesOdp`, `BayesBf` and `BayesBfNormalised` alone; Meyers' CRC alone; compartmental model 1 alone, without its refit comparison) unless `RISK_RS_FULL_BAYES` is set (`prospicio_validation::full_bayes`, the user's decisions of 2026-10-16 and 2026-10-19): pull requests run the smoke version, the nightly and manual (`workflow_dispatch`) runs set the variable. A new slow arm of that kind runs only under the gate, with one cheap model in the smoke run; read the gate at run time (`if full_bayes()`), not with `cfg`, so clippy keeps linting every arm. When a PR changes such a model, run the full version locally too: `RISK_RS_FULL_BAYES=1 cargo test --release ...`
- Integration tests: each file of `validation/tests/` and `crates/prospicio-xll/tests/` is a module of one test binary (`validation`, `bayes`, `fremtpl2` alone; `worksheet` for the add-in), found by the crate's `build.rs`, so a new test file needs no registration line, and one test build links three binaries instead of 105 (#825). Run one file with its module as a filter: `cargo test -p prospicio-validation --test validation reserving_tails::`; an `xll` test file reaches the shared helpers as `use crate::common;`
- Bayesian unit tests: `prospicio-reserving`'s unit tests that sample with NUTS are ignored unless its `slow-tests` feature is on (`#[cfg_attr(not(feature = "slow-tests"), ignore = "...")]`), since in debug they took about 230 s single-threaded and about 5 minutes of CI's rust job. A plain `cargo test` still compiles them, and clippy lints them. Under the same conditions as the parity tests, run them in release (about 70 s on CI's runner): `cargo test --release -p prospicio-reserving --features slow-tests --lib`, as CI's `bayes` job does. A new unit test that fits with NUTS and takes more than about a second in debug gets the same attribute; a cheap check (errors, layouts, gradients, a short run) stays in the debug run. The seed-pinned `bayes::odp::tests::the_one_year_view_is_pinned_by_seed` and the two `the_drops_are_pinned_by_seed` (Mack and ODP one-year views under the drops) stay plainly `#[ignore]`d (platform-specific): run them by name with `-- --ignored the_one_year_view_is_pinned_by_seed` or `-- --ignored the_drops_are_pinned_by_seed`. Each Bayesian model's `the_fit_is_pinned_on_linux` (`bayes::pins`, #841) runs under `slow-tests` and asserts its hash only on Linux x86_64 in release, CI's `bayes` job; when one moves, follow the module doc of `bayes::pins`
- Crates in the WASM scope touched (`prospicio-core`, `prospicio-math`, `prospicio-prob`, `prospicio-aggregate`, `prospicio-pricing`, `prospicio-reserving`, and the umbrella `prospicio`): `rustup target add wasm32-unknown-unknown` once, then `cargo check --target wasm32-unknown-unknown -p <crate>`. No threads, files or C dependencies on their default path
- Python bindings touched: `cargo clippy -p prospicio-python -- -D warnings`, then `cd python && maturin develop && pytest tests`
- R bindings touched: `cargo clippy -p prospicio-r -- -D warnings`, `install.packages("S7")` if missing, `R CMD INSTALL R/prospicio`, then `Rscript validation/scripts/run_r_tests.R` (every test file, a failure not stopping the others, the skipped optional-package blocks listed; give a name fragment to run some files, as `run_r_tests.R reserving`); a test that needs an optional package guards its block with `with_package("pkg")` from `R/prospicio/tests/helper.R`, which the nightly run installs (#845)
- Bindings or their doc comments touched: `cargo xtask generated --check` (needs uv and the R packages `roxygen2`, `pkgload`, `pkgdown`; no site is rendered, #823), and commit the regenerated stub, `man/`, `NAMESPACE` and `R/prospicio/R/extendr-wrappers.R`, which is generated from the installed package and never edited by hand (#836). The sites' configuration or `xtask` touched, or a guide's figures and tables to look at: `cargo xtask docs --check` (also needs Quarto and Python 3.11+ for great-docs), which renders both sites as CI's `docs` job then does
- A new Bayesian reserving model implements `YearModel` (`crates/prospicio-reserving/src/bayes/one_year.rs`, `reserving-bayes.md` decision 17), with its draws stored on an unconstrained scale and carrying with each posterior draw anything the year's cells inform, and passes the one-year conformance suite: `one_year::conformance::check` in its unit tests and an entry in `every_model` of `validation/tests/reserving_bayes_one_year_conformance.rs`. A change to a model that implements `YearModel` (now `BayesOdp`, `BayesBf`, `BayesBfNormalised`, `HierarchicalBf`, `Meyers` and `Compartmental`) re-runs both halves of the suite, the validation half with `RISK_RS_FULL_BAYES=1` (a pull request's CI runs it on `BayesOdp`, `BayesBf` and `BayesBfNormalised` alone)

If a check cannot run in your environment (for example, R is not installed), rely on CI for it and say so in the PR.
